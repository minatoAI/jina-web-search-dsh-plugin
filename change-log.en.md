# Changelog

Full version history of dsh-jina; the "Changelog" section of [README.en.md](./README.en.md) keeps only the latest release.

### 0.8.2 (2026-09-23)

- **fix** **Closed the last two inconsistencies in error propagation** (0.8.0 recorded them as "not changed for now"): the URL check in `jina_read` / `jina_screenshot` / `jina_datetime` used to **return a string** — `'invalid url: undefined (must start with http:// or https://)'` — measured as **`isError: false`**, so the model could read that message as data. The root cause is that the line was a **local regex pre-check** sitting before `callJina` and **never sent a network request**, so it had nothing to do with an upstream status code. It is now `requireUrlArg()` (a line-by-line copy of `requireStringArg`'s contract and message format, reusing `argAt` / `argsReceived`) and it **throws**; the check also moved above `enterExec` to match `runSearch`'s "validate before any side effect", and it is still zero requests. This also fixes the diagnostic defect where `'invalid url: ' + args.url` printed `[object Object]` for an object — the message now reports `(number) 42` / `(string) "example.com"` and adds `did you mean "url" instead of "uri"?` for a likely typo (the alias list `['uri','link','href']` is only used for the hint, never for the value, matching `requireStringArg`'s `['queries','q']`).
- **fix** The **OCR-without-a-key** path in `jina_read` likewise changed from "return a string" to **throw** (wording unchanged). 0.8.0 described it as "returns an actionable message", but it is a **pre-emptive refusal**, not an API response, and a returned value lets the model treat it as a result; throwing makes the harness mark `isError: true` while keeping the "no key detected, no request sent" promise.
- **change** **Upstream errors are now routed by status code**: new `failJina(res)` plus `FATAL_JINA_STATUSES = {401, 422}` — `401` (invalid/missing key) and `422` (illegal arguments) **throw**, because the model has to change its key or its arguments; `0` (network/proxy), `402` (quota), `429` (rate limit) and `5xx` **stay returned**, because their hint exists to be relayed to the user or retried later and must not push the model into "fixing" its own arguments. All nine `if (!res.ok) return describeJinaError(res)` sites became `return failJina(res)` (the `runSearch` one is indented four spaces and was checked individually). **`jina_primer` (`error: describeJinaError(out)`) is deliberately untouched** — it assembles a JSON payload and its tool description promises "the tool never throws". `callJina`'s 401 refresh-and-retry runs before the status decision, so the "successful after a key rotation" path is not affected.
- **test** `test/tool-args.test.js` gains 10 cases (`createHost(reply)` can now inject any helper reply; new `envelope()` / `readerBody()`): the four rejection shapes for the three URL tools (missing / no scheme / wrong type / wrong key name, each asserting `helpers.length === 0`), a positive case proving a valid URL is still sent verbatim (`body.url`, with a 400-character body so the selector retry cannot fire and `helpers.length === 1` holds), OCR without a key still sending nothing, and four routing regressions — 401 throws / 422 throws / 429 returns / `jina_primer` never throws. The old "OCR without a key" assertion in `test/reader-headers.test.js` was updated from "returns a string" to expect a throw (it depended on the old shape). Full suite: **114 tests, 113 pass, 1 skipped (`JINA_LIVE_PROXY`, opt-in), 0 fail**.
- **verify** Static checks: `grep -n "return failJina(res)" index.js` = 9 lines; `grep -n "describeJinaError" index.js` leaves only the definition, the call inside `failJina`, and `jina_primer`'s payload assembly (`error: describeJinaError(out)`); `grep -n "return 'invalid url" index.js` = 0 lines. Before the change `test/` had **zero coverage** of `401` / `422` / `invalid url` / `describeJinaError`, so change C had no old assertions to migrate — the only one needing an update was the OCR case hit by change B.

### 0.8.1 (2026-09-23)

- **fix** **Fixed the reader-options block on the settings card being entirely greyed out, with both save buttons dead** (reproduced from a user screenshot): dsh `601d6761e4` (`feat(settings): project volatile Config through profile-backed forms`) **removed `settings.register(ns, schema)`** — a settings namespace is now the **Loader/profile composition entry id**, a plugin declares its live fields by exporting a schemastery-shaped `Config` whose field nodes carry `meta.volatile`, and the harness hands the resolved config to `apply(ctx, config)` as its second argument (resolved through Standard Schema's `'~standard'.validate`). The old code called `sctx.settings.register(...)` inside `ctx.inject(['settings'], …)`, which throws `TypeError: sctx.settings.register is not a function`; the plugin's own try/catch swallowed it, so the `jina-tools` namespace never appeared in `settings.describe().namespaces`, the browser half's `loadProxy()` found no matching row → `phase = 'unavailable'` → every control `disabled` (`optsReady = phase === 'ready' && writable`). The greyed-out form in the screenshot is that symptom — **not CSS, not permissions, not a read-only profile** — and the same root cause meant nothing could be persisted to `settings.yaml` either.
- **fix** **Saving applies immediately: no restart, no remount.** The new mechanism requires each field node to carry `meta.volatile`, and the resolved config holds one **cross-copy-safe** volatile reference per field (`Symbol.for('cosmokit.volatile.write')`, the same Symbol the bundled `cosmokit` uses). On save the harness only writes the new value into those references (`updateVolatile`): `fiber.config` keeps its object identity, the plugin is not remounted, and it re-reads `settingsSnapshot(config)` on every operation — exactly the same "re-resolve per call" contract the API key already had.
- **fix** The root node must **not** be volatile as a whole: `volatileForm()` would treat the entire config as one reference and `strip()` would then drop every non-field key (fields added by a future version, hand-edited entries). Per-field `meta.volatile` keeps undeclared keys intact (pinned by a regression test).
- **fix** `Config['~standard'].validate` must return a **plain object synchronously**: `resolveConfig()` throws `TypeError('Async config validation is not supported')` on a thenable and a cordis `ValidationError` on `issues`, and `volatileEntries()` only descends into plain objects (`Object.getPrototypeOf === Object.prototype`) — anything else silently kills the whole settings channel. The validator stays tolerant of `undefined` / non-objects / hand-mangled values (it always returns the eight refs and hands the raw value to `toolSettingsOf()` for normalization), so no profile composition can make `describe()` throw — and `describe()` is **shared by the entire Plugins settings page**, so a throw there breaks every plugin's card, not just this one.
- **fix** `Config.toJSON()` must return **fresh nodes on every call**: `plainSchema()` walks the result and `delete`s `node.meta.volatile`, so reusing one dict would degrade every later save into a full plugin remount. Each field node also needs its own `toJSON()` and a `meta` object (schemastery's string resolver dereferences `meta.loose`).
- **change** The host half no longer injects `settings`; the `/api/dsh-jina/primer` payload's `settingsError` field became `settingsLive` (a boolean health check: does the resolved config really hold volatile refs?), which is what the card's diagnostics block now reports.
- **test** `test/proxy.test.js`, `test/reader-headers.test.js`, `test/plugin-proxy.test.js` and `test/tool-args.test.js` all migrated to the new seam (`Config['~standard'].validate(raw).value` → `apply(ctx, config)`), with new assertions: all eight fields carry `meta.volatile` and survive `toJSON()`, the validator's tolerant surface, fresh nodes per `toJSON()` call, and two end-to-end regressions — **an option or proxy address saved on the card takes effect on the very next tool call without a restart** (the proxy one also asserts no further WinINET registry probe once an address is saved). Full suite: 104 tests, 103 pass, 1 skipped (`JINA_LIVE_PROXY`, opt-in).
- **verify** Checked against the **real** components (not mocks): `packages/settings/settings/lib/index.js` (the package `main`, i.e. the copy the running server loads) for `SettingsForms.describe()/mutate()`, `lib/types/schema.js` for `plainConfig`/`volatileForm`/`projectForm`/`isVolatilePath`, `cordis-plugin-loader/lib/types/config/diff.js` for `equalExceptVolatile`, and the profile's `@deepseek-ai/cosmokit` for `volatileEntries`/`updateVolatile`/`deepEqual`. With a faithful `configEditor` stand-in replicating `resolveConfig`, this proved: the eight volatile refs sit at the right paths, `volatileForm(Config)` is non-undefined, `projectForm(form, plainConfig(resolved))` is an identity, repeated `describe()` calls do not strip `meta.volatile`, a full `describe() → mutate()` round trip works (`applies: 'live'`, revision fencing, the `base`/`user`/`value` layering, `unset` falling back to the inherited value, a stale revision raising `SettingsConflictError`, a non-volatile path rejected), and `equalExceptVolatile(fiber.config, candidate, Config) === true` — proving the **live-update** path rather than a remount.

### 0.8.0 (2026-09-18)

- **feat** **`jina_read` gains an OCR switch (jina-ocr-v1)**: with `ocr: true` (or the card default) reads go through `X-Respond-With: jina-ocr-v1` — the vendor's 3.4B document parser, which turns a scanned page, image-heavy PDF or formula/table-heavy document into Markdown in one pass (tables as HTML, formulas as LaTeX), in English and Chinese. Multi-page documents can be steered with the `page` parameter (`X-Page`). The model costs roughly **40x the tokens**, and the **Reader rejects it for anonymous callers** (measured: `Authentication is required to use this feature (Vision Language Model / OCR)`), so the plugin **sends no request** when it cannot resolve a key and returns an actionable message instead.
- **feat** **Three zero-side-effect parameters on every read**, each verified against the official OpenAPI document and parameter panel: `X-Preset: agent` (the vendor's preset for AI agents — the docs state a preset **only fills options the caller did not set explicitly**, so it can never override an explicit parameter), `X-Base: final` (resolve relative links against the post-redirect URL), `X-Timeout: 120` (matched to the client's own 120 s ceiling — sending the documented maximum of 180 would be pointless, since the client gives up first and reports its own timeout; raise both together or neither).
- **feat** **Selector group on by default, with an automatic fallback**: reads now send a conservative `X-Target-Selector` (article containers only) and `X-Remove-Selector` (header/footer/nav/cookie banners/ads/sidebars/comments), plus new per-call parameters `targetSelector`, `waitForSelector`, `removeSelector` and `noCache`. `X-Target-Selector` **implies** a matching `X-Wait-For-Selector` and returns an empty page when nothing matches — so a first result shorter than 200 characters is **retried without the selector group**, keeping whichever body is longer (`SELECTOR_RETRY_MIN_CHARS`). The remove list deliberately omits `.modal` / `.popup` / `.overlay`, which can be the content container in an SPA.
- **feat** **Configurable image policy**: `X-Retain-Images` is no longer hardcoded to `none`; it defaults to the API default `all` (with `alt` / `none` selectable). The `images` / `links` parameters still append the image/link summaries.
- **feat** **New "reader options" block on the settings card**: OCR switch, image-policy select, alt-text toggle, selector-group toggle and the two selector overrides. Every field lives in the same `jina-tools` namespace and rides the **same revision-fenced write path** (`mutate(NS, ops, proxyView.revision)`), so the two blocks cannot clobber each other.
- **fix** **`X-With-Generated-Alt` now defaults to off**: it is a paid feature (anonymous callers get the same 401: `Authentication is required to use this feature (Alt text generation)`) and is **mutually exclusive with `X-Respond-With`** (the docs state alt generation does not work when `X-Respond-With` is set). More importantly, **supplying a key is what makes a read billable** — defaulting this on would silently turn every anonymous (free) read into a charged one for any user who has a key. It is therefore opt-in, and only sent on the non-OCR path with a key present.
- **fix** **`createSettingsSchema()` used to keep only `proxyUrl`**, so a newly added field was silently dropped and could never be saved. It now keeps every known field (type-checked, unknown keys dropped), and a new `toolSettingsOf()` resolves "unset" into the documented defaults. The stored document still holds **only deviations**, so a later default change reaches users who never touched that field (an existing `settings.yaml` with just `proxyUrl` is unaffected).
- **fix** **A required argument is no longer silently coerced into the string `"undefined"`** (defect found in a real session): `ctx.tools.register` hands `parameters` to the model API but **never validates at runtime** (validation lives only on the first-party `defineTool` path), so a key the model got wrong reaches the executor untouched. `String(args.query)` then turned a missing `query` into the four-character search term `undefined`, and Jina answered with MDN's `undefined` page — a **well-formed, `isError: false`** result that reads exactly like a real search. Measured in the wild: the model sent `jina_web_search` `{"queries":[...],"num":6}`, because the built-in `web_search` takes `queries`, this plugin takes `query`, and both are registered side by side. The `query` of `jina_web_search` / `jina_search_arxiv` / `jina_search_ssrn` / `jina_expand` / `jina_rerank`, the `texts` (and `labels`) of `jina_embed` / `jina_classify`, the `documents` of `jina_rerank` and the `url`-or-`arxivId` pair of `jina_pdf` are now checked up front and **throw** (the harness turns that into `isError: true` with an `Error:` prefix — the only shape that makes the model stop and fix the call, since a returned error string is still a successful result). The message names the tool, the parameter, the expected type and the keys actually received, and adds a hint when the key looks like a typo (`did you mean "query" instead of "queries"`). The check runs before `enterExec` and `callJina`, so **no request is spent**. Known remaining inconsistency: the URL checks in `jina_read` / `jina_screenshot` / `jina_datetime` still return a string; they cannot produce a plausible-looking fake result, so they were left alone.
- **change** `jina_read` now always asks for `Accept: application/json` and unwraps the envelope into markdown: a `Title` / `URL Source` / `Published Time` header plus a `[Usage: ...]` footer, with an unparsable body returned verbatim rather than dropped.
- **test** Added `test/reader-headers.test.js` (14 cases): it decodes the network helper's stdin and asserts the headers that actually reach the wire — the three fixed parameters, the image policy, the selector group and its retry, the OCR switch with `X-Page`, zero requests when no key can be resolved, the three alt-text constraints (opt-in, key-gated, mutually exclusive with OCR), JSON-envelope unwrapping with usage, verbatim fallback for an unparsable body, schema field retention and the `toolSettingsOf` defaults. `test/client-render.test.js` gained render assertions for the new controls, and `test/client-bundle.test.js` gained field-wiring and single-write-path assertions. A new `test/tool-args.test.js` (9 cases) opens with **the exact wrong call from the field** (`{queries:[...],num:6}`), covers missing / empty / whitespace-only / wrongly typed / `undefined` arguments, asserts the message names the parameter and the suspected typo, asserts `helpers.length === 0` (a rejected call must not spend a request), and locks the valid path down with one positive case (`body.q` reaches the API unchanged).

### 0.6.1 (2026-09-16)

- **fix** Fixed the browser-half crash 0.6.0 introduced, which made the whole **Jina Tools card disappear** (reported from a live console: `Error: cannot get property "remote.settings" without inject`, then `slot entry crashed in 'settings.plugin.item'`). The mechanism was reproduced and re-verified against the real cordis runtime (injecting only `remote` reproduces the original error; adding `remote.settings` resolves).

### 0.6.0 (2026-09-15)

- **feat** **Manual local-proxy configuration**: the Jina Tools card (Settings → Plugins → Configure) gains a "Local proxy (optional)" block — type the address (`http://127.0.0.1:7897`, the scheme may be omitted), save, and the next tool call uses it; one click clears it back to automatic detection. The value is stored in the `proxyUrl` field of the plugin's own `jina-tools` settings namespace (persisted in the settings document, hand-editable via `settings.yaml`). This is the fix for the common setup where the proxy client listens on a loopback port without being the Windows system proxy: WinINET reports `ProxyEnable = 0x0`, automatic discovery cannot see it, and earlier versions went direct and failed.
- **feat** Proxy precedence (`proxy.js`, pure and unit-tested): tool-level override > card `proxyUrl` > `JINA_PROXY_URL` environment variable > WinINET system-proxy discovery (port-change self-healing kept) > the inherited startup environment (`HTTP_PROXY` / `HTTPS_PROXY`). A configured manual address skips the registry probe entirely, and a transport failure never silently swaps it for an auto-discovered one — the error names it instead.
- **feat** Visible diagnostics: `/api/dsh-jina/primer` (the card's health check) now reports **the proxy the probe actually ran through** plus any saved-but-unusable address with its reason (e.g. `socks://` is not usable by the Node fetch helper); transport failures name the proxy in play and state the next step (check the port / clear to re-enable auto-detection / fill in the local proxy).
- **fix** Only `http://` / `https://` proxies reach the network helper: Node's `fetch` exits at startup when `NODE_USE_ENV_PROXY` sees a non-http(s) scheme, so a `socks5://` address is now refused with an explanation instead of being silently ignored or breaking the helper.
- **refactor** The proxy policy and the settings schema moved into a zero-dependency pure module (`proxy.js`); the network helper script is exported as `HTTP_HELPER_SCRIPT` so the transport can be verified end to end.
- **test** New `test/proxy.test.js` (20 pure-function contract cases), `test/plugin-proxy.test.js` (13 mock-host integration cases: namespace registration, precedence, helper environment construction, error text, primer payload, plus an opt-in live case that really spawns the helper through `http://127.0.0.1:7897` with `JINA_LIVE_PROXY=1`), and `test/client-bundle.test.js` (8 browser-bundle contract cases: registration id / namespace key / settings transport / revision fencing — the bundle has no build step, so a syntax error would otherwise surface only at runtime).
- **verify** Checked against the real components (not mocks): `createSettingsSchema()` was registered with a real `@deepseek-ai/dsh-settings-file` provider through the real `settings.register` / `mutate` / `describe({redactSecrets:true})` (the address lands in `settings.yaml`, the revision advances, `secrets: []` treats it as plain configuration), and the emitted schema was rehydrated with the real schemastery 3.18.2 `new Schema(serialized)` exactly as the browser does (accepts a string, rejects a number). Driving the plugin off that real settings service then showed the stored address on the helper environment (both casings + `NODE_USE_ENV_PROXY=1`) with no registry probe, and `undefined` again after clearing (full inheritance of the harness environment). Separately, the shipped helper ran in a clean process: `HTTPS_PROXY=http://127.0.0.1:7897` + `NODE_USE_ENV_PROXY=1` → `r.jina.ai` answered 200; `127.0.0.1:1` → `fetch failed (connect ECONNREFUSED 127.0.0.1:1)`, the path whose error message names the configured address.
- **docs** README gains a "Local proxy" section (steps, precedence, `JINA_PROXY_URL`, trust boundary) and the development notes cover `proxy.js` and the new tests.

### 0.5.3 (2026-09-05)

- **compat** Verified against dsh v0.1.3-alpha.1 ([releases](https://github.com/deepseek-ai/deepseek-harness/releases)): the breaking changes (Session persistence API now owned by lifecycle-scoped `SessionHandle`s; async `agentLoop.create()`; new session lock holding each session in at most one process; Session format v2) are all host-internal — the plugin only uses `tools` / `subprocess` / `fs` / `credentials` / `webServer` / `settings` / `sandboxPolicy` plus `exec.agent.session.header.cwd` / `exec.signal`, and each face was checked against the 0.1.3 sources with no migration needed: `tools.register` parameter normalization (`normalizeRegisteredParameters`), `output {schema, render}`, `credentials.resolve`, the standalone `remote.credentials` service injection, the `credentials/reference-updated` event (still forwarded by `remote`), `webServer.register` (exact route), the empty-namespace `settings.register`, the keyed `settings.plugin.item` slot (`key: 'jina-tools'`), the `window.__ModuleLoader__` registration id (graph row id = exact package name `dsh-jina`), and `subprocess.spawn` (`SubprocessOutcome` via `handle.done` + offset-based `collected` reads + `resolveExecutable`) are all unchanged. The oh-my-dsh upgrade cards for 0.1.2-alpha.1 → rc.1 (`RemoteError` namespaces, `Session.events` removal, `report` → `send_message`, PTC `workflow` / `web_fetch` defaults, etc.) were cross-checked too: none of them hit this plugin.
- **fix** Proxy environment aligned with the 0.1.3 outbound proxy policy: `subprocess` merges `env` over a scrubbed base that already carries the harness-resolved proxy (`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY` from the startup environment + `NODE_USE_ENV_PROXY`); the old `makeEnv` always wrote `NO_PROXY: ''` (wiping the base bypass including loopback) and unconditionally set `NODE_USE_ENV_PROXY=1` (which breaks the Node helper startup under a SOCKS proxy). Fix: return `undefined` when there is no discovered/overridden proxy (fully inherit the harness policy); with a proxy, write both env-name casings, never touch `NO_PROXY`, and only carry the flag for http(s). Windows system-proxy discovery (WinINET, with port-change self-healing) stays as the complement to the env policy.
- **docs** README "Network & proxy" section updated for the env-proxy inheritance.

### 0.5.2 (2026-08-29)
